# Интеграция #121 в архитектуру PyAudioTranscriptor

**Задача:** анализ того, как фича **#121** (анализ видеоряда: OCR слайдов/схем + определение
активного говорящего) встроилась бы в существующую архитектуру.
**Режим:** только чтение репозитория; код не менялся; сервер 8790 не трогался.
**Факты** — со ссылками `path:line`. Непроверенные/предполагаемые вещи помечены **[предположение]**.

---

## 0. TL;DR (выводы)

1. **Сейчас видеоряд не анализируется вообще.** Из видеофайлов берётся только аудиодорожка:
   `load_waveform` открывает контейнер и декодирует `container.streams.audio[0]`
   (`utils/audio.py:136,145`). Кода для кадров/OCR/детекта лиц-плиток нет нигде
   (grep по `tesseract|opencv|cv2|PIL|keyframe|scene` — пусто).
2. **Конвейер строго линейный и синхронный** (`pipeline.py:572`, порядок стадий — `pipeline.py:675-1079`).
   Врезка тяжёлого OCR прямо в основной прогон ударит по слабому железу и по UX ожидания.
3. **Рекомендация (bare minimum):** два независимых куска:
   - **(A) OCR слайдов — опциональный пост-шаг по кнопке** (аналог «Сформировать протокол»,
     `protocol.py:94` + `app.py:3007`), не в основном прогоне.
   - **(B) активный говорящий — тоже пост-шаг** (кадры + сопоставление с уже готовой стенограммой
     и/или с сегментами диаризации из кэша), результат — **слабая подсказка**, а не замена диаризации.
4. **Модель данных:** аддитивное поле `slides` в JSON-результате (`web/results.py:127`) + sidecar-каталог
   картинок `*.slides/` (по образцу `*.speakers/`, `diarization/samples.py`, `runner.py:680`).
   Отдельная стадия кэша `slides` (`StageCache`, `cache/store.py:48`).
5. **Основные риски:** платформенно-зависимый OCR-бинарь (упаковка #118), непокрытая эвикцией
   папка картинок (`cache/store.py:217` знает только `*.json`/`*.wav`), сопоставление «плитка → id
   говорящего» без распознавания лиц принципиально приблизительное, таймскейл видео vs аудио.
6. **Оценка объёма (T-shirt):** только OCR-слайды — **L (14–20 SP)**; OCR + активный говорящий — **XL (21+ SP)**.
   Согласуется с вердиктом TODO.md: «Сложность: высокая» (`TODO.md:716`).

## 1. Как устроен конвейер сегодня (необходимый контекст)

### 1.1. Стадии и порядок

`run_pipeline` (`pipeline.py:572`) — строго последовательный:
денойз → ASR → диаризация → enrollment → merge → очистка → коррекция → LLM → `TranscriptionResult`
→ экспорт → образцы голоса → `done`.

- ASR: `pipeline.py:705-744`, кэш `asr` (`pipeline.py:706-738`).
- Диаризация: `pipeline.py:752-825`, кэш `diarization`.
- Enrollment (имена по образцам голоса): `pipeline.py:838-882`.
- Единый waveform `_SharedWaveform` (`pipeline.py:110`), освобождается после диаризации/enrollment
  (`pipeline.py:884-898`, `release()` — `pipeline.py:162`). **Комментарий прямо про 230 МБ/час.**
- Merge/clean/correct/LLM: `pipeline.py:900-1010`.
- Сборка результата: `pipeline.py:1012-1021`; экспорт: `pipeline.py:1024-1049`; образцы: `pipeline.py:1051-1077`.

### 1.2. Доменная модель

`TranscriptionResult` (`domain/models.py:145-160`): `source_path, language, duration, entries, speakers,
participants, summary, low_confidence_threshold`. **Места под слайды/активного говорящего нет.**
`TranscriptEntry` (`domain/models.py:90-142`) уже расширялся аддитивно (`words`, `edited`, `overlap`),
то есть прецедент «новое необязательное поле» есть.

### 1.3. Кэш

`StageCache` (`cache/store.py:65`): ключ — `compute_cache_key` = SHA-256(`cache_version` + `stage` +
identity файла {path,size,mtime_ns} + params) (`store.py:48-62`, `store.py:39`).
Формат: JSON-файл на ключ (`store.py:98`) + опционально `.wav` (`store.py:101`).
Сериализаторы есть только для ASR и диаризации (`cache/serialization.py`, функции на `:81` и `:124`).
Эвикция (`store.py:227`) и `clear` (`store.py:266`) смотрят **только `*.json`/`*.wav` верхнего уровня**
(`store.py:217`) — подкаталоги не трогаются.

### 1.4. Видео как вход

Видеофайлы уже принимаются: `MEDIA_EXTENSIONS` содержит `.mp4/.mkv/.mov/.webm/.avi/...` (`web/app.py:302-329`).
PyAV открывает видеоконтейнер, но `load_waveform` берёт только аудиопоток (`utils/audio.py:136-172`).
`probe_duration` (`estimates.py:739`) тоже читает `container.duration` — для видео работает.
**Вывод: видео уже «ходит» по конвейеру как аудио, кадры просто игнорируются.**

### 1.5. Веб-слой

- Контракт API: `serialize_result` (`web/results.py:127`), `entry_to_dict` (`web/results.py:82`),
  легенда меток `MARKS` (`web/results.py:26-41`), round-trip `result_from_payload` (`web/speakers.py:47`).
- Воркер один и последовательный (`web/runner.py:151`, `_worker` `:301`), результат пишется в
  `web-data/results/{job_id}.json` в `_finish_success` (`web/runner.py:581-655`).
- «Постобработка по кнопке» уже есть: `POST /api/jobs/{id}/protocol` (`web/app.py:3007`) →
  `generate_protocol` (`protocol.py:94`); прогресс действия идёт через шину действий (`app.py:3023`,
  `ACTION_PROTOCOL`). Аналогично correct-text/apply-glossary (`app.py:2868`, `:2769`).
- План стадий для UI: `STAGES` (`web/estimates.py:45-54`), `_STAGE_FLAGS` (`:58`), `planned_stages` (`:70`).
- Фронт: вкладки задачи `TABS` в `webui/src/pages/JobPage.tsx:26-32`
  (Стадии/Спикеры/Стенограмма/Чат/Экспорт); экспорт — `webui/src/pages/job/ExportTab.tsx`.

### 1.6. Конфиг

`AppConfig` (`config/settings.py:105`), значения по умолчанию — `config/defaults.py`.
Для веба конфиг задачи собирается `build_job_config` (`web/config.py:188-391`) из `config.env` +
`web-data/settings.json`; редактируемый срез — `WebSettings` (`web/settings.py:112`).
CLI-флаги — `cli/app.py` (напр. `--diarization/--no-diarization`, `:302`).

### 1.7. Смежное

- Диаризация: `diarization/*` (движки pyannote/nemo-speech/hybrid/sherpa; #47/#63 — в `TODO.md:694`).
- Память/слабое железо: `docs/architecture/memory.md:13-29` (RAM определяет ASR; 230 МБ/час waveform;
  4 ГБ = «whisper-cpp base/small + диаризация off/sherpa + без денойза/LLM»).
- Пресеты железа #144/#146: `web/settings.py:83-105`, `apply_hardware_preset`.
- Опциональные зависимости уже организованы extras-ами в `pyproject.toml:32` (gigaam/sherpa/torch).

## 2. Варианты интеграции

### Вариант (а) — новая стадия конвейера `slides`/`video` (в основном прогоне)

Плюсы: единый прогресс/отмена/кэш; результат готов сразу в JSON.

Минусы:
- OCR — **очень медленный на CPU** (порядка десятых–секунд на кадр на слабом железе) **[предположение,
  требует замера]**, а основной прогон уже упирается в ASR/диаризацию (см. `memory.md:13-17`).
- Обязателен для всех видео на каждом прогоне, если включён — ломает профиль «Слабое железо».
- Стадийный пайплайн линейный; «активный говорящий» логически зависит от merge/диаризации, а OCR — нет.
  Это разрывает единый «stage» на два с разными зависимостями.
- `TranscriptionResult` и контракт API меняются до того, как фича доказала пользу.

Куда бы встал: OCR — сразу после ASR (не зависит от говорящих); активный говорящий — после диаризации
(`pipeline.py:825`) и/или после merge (`pipeline.py:903`).

### Вариант (б) — опциональный пост-шаг по кнопке (рекомендуется)

Плюсы:
- Точная копия существующего паттерна «протокол по кнопке»: `protocol.py:94` +
  `app.py:3007` + шина действий (`ACTION_*`) + синхронный вызов в рабочем потоке FastAPI
  (комментарий `app.py:3007-3022`). Для OCR это идеально: **не блокирует очередь**, запускается осознанно.
- Не трогает основной прогон и стадии `STAGES`; на слабом железе просто не используется.
- Работает поверх **уже готового** результата (стенограмма + говорящие) → активный говорящий
  сопоставляется с финальными репликами, а не с промежуточными сегментами.
- Мягкая деградация и права/кэш переиспользуются.

Минусы: нужен отдельный UI-вход и отдельный эндпоинт; OCR не «бесплатен» (считается по запросу) —
но это и есть цена опциональности.

### Рекомендация

**Вариант (б)** для обоих подпунктов, как bare minimum; **синхронно по кнопке** (как протокол),
с отдельными эндпоинтами:
`POST /api/jobs/{id}/slides` (кадры + дедуп + OCR) и, при желании, тот же вызов с флагом
`detect_speaker=true` (активный говорящий по кадрам + сопоставление с репликами).
Асинхронный фон/очередь — **не** в MVP (усложняет; очередь уже одно-поточная, `runner.py:151`).

Почему не «после ASR, но в основном прогоне»: активный говорящий требует говорящих, а OCR — нет;
дробить основной пайплайн на два зависимых места ради опциональной тяжёлой фичи неоправданно.

## 3. Модель данных

### 3.1. Слайды (кадр → время → текст)

Предлагаемые доменные модели (новый модуль, напр. `domain/models.py` или `video/models.py`):

```
SlideFrame:
  index: int
  start: float          # время появления слайда (сек от начала)
  end: float            # время исчезновения (до следующего распознанного слайда)
  text: str             # OCR-текст
  confidence: float|None
  image: str|None       # относительный путь к кадру (sidecar)

ActiveSpeakerHint:
  start: float
  end: float
  tile: int             # индекс «плитки»/дорожки на кадре (или позиция)
  speaker_id: str|None  # сопоставление с говорящим результата (если удалось)
  confidence: float
```

### 3.2. Хранение: sidecar vs поле результата

- **JSON-результат — аддитивные поля.** Как `words` добавляется в реплику только когда есть
  (`web/results.py:105-107`), а `samples` — отдельным полем (`runner.py:590-591`), так добавляются
  необязательные `slides: [...]` и `active_speaker_hints: [...]`. Старые клиенты/экспортёры
  (`result_from_payload`, `web/speakers.py:47`) их игнорируют → **обратная совместимость сохраняется**.
- **Картинки кадров — sidecar-каталог** `*.slides/` рядом с результатом, по образцу
  `*.speakers/<Имя>.wav` (`diarization/samples.py:samples_directory`, потребление — `runner.py:680-692`).
  В JSON хранится относительный путь (как `samples` в `runner.py:686-692`).
- **Доменная модель** `TranscriptionResult` (`domain/models.py:145`) получает опциональные поля
  `slides`/`active_speaker_hints` (по умолчанию пустые) — так экспортёры и LLM смогут их видеть.

### 3.3. Привязка к таймкодам/репликам

- Слайд привязывается к интервалу `[start, end]`; на UI/экспорте — к репликам, чьи интервалы
  пересекаются (по аналогии с `apply_overlap_regions`, `pipeline.py:951-954`).
- **Активный говорящий — только подсказка.** Из кадров нельзя получить те же `speaker_id`, что даёт
  диаризация (`Speaker N`, `domain/models.py:66`). Правильный bare-minimum: сопоставлять **смены
  подсвеченной плитки** с интервалами реплик и/или сегментами диаризации; при неоднозначности —
  `speaker_id=None`. **Распознавание лиц — вне рамок** (это уже не «минимум»).

## 4. Поток данных

### 4.1. Нарезка кадров (PyAV)

Сейчас PyAV применяется только к аудио (`utils/audio.py`). Для видео нужен **новый модуль**,
например `utils/video.py`, по образцу `load_waveform`:
`av.open(path)` → `container.streams.video[0]` → `container.decode(video_stream)` →
`frame.pts * video_stream.time_base` = время кадра. Есть готовый образец работы с `time_base`
в аудиокоде (`utils/audio.py:73`, `:119-123`) и предупреждение про сброс/дрейф таймскейла (#14,
`utils/audio.py:150-163`) — **[риск]** переменный frame rate и рассинхрон шкал видео/аудио нужно
проверять отдельно.

### 4.2. Дедуп и порог стабильности

- Сэмплирование раз в N секунд (экономия) + детект смены сцены (perceptual hash / SSIM / ffmpeg
  `select=gt(scene,\u2026)`) **[предположение — конкретный метод за выбором]`.
- Порог стабильности: слайд считается «показанным», если N подряд похожих кадров удерживаются ≥ T секунд
  (иначе пропускаем переходы/анимации).
- Дедуп одинаковых слайдов (один слайд, показанный дважды) — по хэшу текста/изображения.

### 4.3. Куда идёт OCR-текст

Варианты (можно комбинировать, начиная с минимального):
1. **Отдельная панель/вкладка «Слайды»** в задаче — основной bare-minimum.
2. **В резюме/протокол** — OCR-текст с таймкодами подмешивается в контекст LLM-резюме
   (`llm/summary.py`, вызывается из `protocol.py:74` и `pipeline.py:995`). Опционально (галочка).
3. В экспорт «Слайды» (MD/PDF) — см. §6.

**Важно:** не «загрязнять» стенограмму. Слайды — отдельный слой, сшиваемый по таймкоду, а не текст
внутри реплик.

### 4.4. Активный говорящий

Поток: кадры → детект смены подсвеченной плитки (эвристика по раскладке: Teams/Zoom gallery vs
screen-share) → интервалы плитки → сопоставление с репликами результата → список `ActiveSpeakerHint`.
Применение: ослабить `speaker_confidence` / показать метку «подсказка: активен Спикер N» рядом с
существующими метками (`web/results.py:26-41`). **Не перезаписывать** результат диаризации.

## 5. Кэш / производительность / память

### 5.1. Ключ кэша

Новая стадия `slides` в `StageCache` (`cache/store.py:48`). В `params`:
`frame_interval`, `scene_threshold`, `dedup_threshold`, `ocr_engine`, `ocr_model`, `ocr_lang`,
`min_slide_seconds`, `impl_version`. Identity файла берётся автоматически (`store.py:39`).
Отдельная стадия `active_speaker` (или тот же ключ с флагом) — параметры детекта плитки.

### 5.2. Стоимость

- Декод видео: умеренный, но O(числа сэмплируемых кадров).
- OCR: главный драйвер времени, **на CPU дорого**; отсюда — пост-шаг, а не основной прогон.
- Хранить кадры надо по одному (декод → сохранить PNG/JPEG → отпустить), не держать все в RAM.

### 5.3. Память и слабое железо

Прямо согласуется с `docs/architecture/memory.md:13-29`: OCR добавляет отдельный процесс/модель,
поэтому:
- зависимость — **опциональный extra** в `pyproject.toml` (паттерн `pyproject.toml:32`),
  импорт ленивый, отсутствие — мягкая деградация (как денойз/LLM);
- фича не входит в пресет «Слабое железо» (`web/settings.py:83-90`);
- RAM-бюджет: не поднимать `_SharedWaveform` заново (он уже освобождён, `pipeline.py:893-894`);
  кадры — на диск, не в память.

### 5.4. Ограничения кэша (риск)

`StageCache._iter_entries` (`cache/store.py:209-225`) и `clear` (`:266-281`) учитывают только
`*.json`/`*.wav`. **Каталог картинок слайдов не будет эвиктиться/чиститься.** Либо складывать картинки
внутрь отслеживаемого каталога с расширением, покрытым эвикцией, либо расширить `StageCache`
(отдельная папка + собственный учёт) — это отдельное решение, явно фиксируемое в ADR.

## 8. Риски и открытые вопросы

1. **OCR-бинарь и упаковка.** Tesseract/PaddleOCR требуют системных бинарников/моделей —
   та же проблема, что у `deep-filter`/`whisper-cli` (позиция #118, `TODO.md:700`). Windows/macOS
   нейтрально **не решается** без отдельной работы по бандлингу.
2. **Эвикция картинок не покрыта** (`cache/store.py:217`, `:274`) — см. §5.4.
3. **Раскладка видео неизвестна.** «Подсвеченная плитка» активного говорящего есть не во всех
   записях/раскладках; галерея, screen-share и запись с одним спикером ведут себя по-разному.
   **[Открытый вопрос: какой тип видеоряда целевой?]**
4. **Сопоставление плитка → `speaker_id`** без распознавания лиц приблизительно; нужен явный
   сценарий «подсказка, при низкой уверенности — молчим» (как enrollment: ниже порога — не присваивать имя,
   `defaults.py:37-40`).
5. **Таймскейл видео vs аудио** (VFR, дрейф). Прецедент #14 (`utils/audio.py:150-163`) показывает,
   что рассинхрон здесь уже ломают тесты — нужен отдельный тест на выравнивание.
6. **Детерминизм и кэш:** OCR/дедуп нестабильны между версиями → обязательный `impl_version`
   в ключе (паттерн `pipeline.py:400`).
7. **Диск:** кадры слайдов на длинные записи могут занять много места; нужен лимит/размер превью.
8. **Приватность:** OCR кадров чувствительных встреч — обрабатывать только локально (соответствует
   текущему «localhost по умолчанию», `TODO.md:756`).
9. **Производительность:** реальная скорость OCR на CPU и RTF видео-дека не измерены — **[нужен замер]**.
10. **Контракт API**: добавление полей безопасно, но экспортёры/чат/редактор говорящих должны
    корректно игнорировать `slides` (проверяется round-trip `result_from_payload`, `web/speakers.py:47`).

### 9.2. Use Case Points (UC)

Акторы: Пользователь (Average = 2), внешний OCR-инструмент (Simple = 1). **UAW = 3**.

| Вариант использования | Вес |
|---|---|

| Экспортировать слайды (MD/PDF) | Simple = 5 |
| Подсказка «активный говорящий» | Complex = 15 |

**UUCW = 45.**

TCF (только критичные факторы): производительность (OCR/декод — существенно), требования повторного
использования (общие компоненты), распределённость данных — нет. Для bare-minimum примем 3 значимых
фактора со средним весом → **TCF ≈ 1.0–1.1**.
EF (только 2 фактора из методики): опыт команды + зрелость инструментов — оба на существующем стеке
(высокие) → **EF ≈ 0.8–0.9**.
`UCP = UUCW × TCF × EF ≈ 45 × 1.05 × 0.85 ≈ 40` (без активного говорящего ≈ 32).
Плюс: это **не** greenfield — инфраструктура кэша/веба/экспорта уже есть, что снижает фактическую цену
относительно UCP.
