Инструмент для подготовки стенограмм переговоров, интервью и судебных
материалов: распознаёт речь, определяет, кто из собеседников что говорит,
склеивает реплики в предложения, а затем может уточнить имена участников и
терминологию локальной LLM — и экспортирует стенограмму в удобном формате с
явной разметкой говорящих.

Работать можно тремя способами. Основной — **веб-интерфейс**
(`audio-transcriber web`): полный интерфейс в браузере с очередью,
стенограммой, протоколом и настройками. Для скриптов и автоматизации есть
**CLI** (`audio-transcriber transcribe`), а для тех, кто предпочитает
терминал, сохраняется **TUI** на Textual — но он больше не развивается и не
является основным путём.

Вся обработка выполняется полностью локально, без обращения к облачным API —
аудио и текст никогда не покидают ваш компьютер.

## Возможности

- **Веб-интерфейс** (`audio-transcriber web`) — основной способ работы:
  - **очередь задач** с загрузкой и удалением файлов; **число говорящих**
    задаётся при постановке в очередь (по умолчанию «авто»);
  - **живой прогресс** по стадиям через SSE, с **длительностями стадий и общим
    временем обработки**;
  - **стенограмма** с поиском и пометками, **прослушивание фрагмента прямо из
    реплики** (▶), правка говорящих (переименование, объединение) и
    **«Применить имена»** по образцам голоса;
  - **библиотека голосов** (загрузка, прослушивание, переименование, удаление;
    сохранение образца говорящего из задачи);
  - **глоссарий**: источники с галочками, добавление/удаление записей, импорт
    TXT/CSV;
  - **«Сформировать протокол»** по кнопке (резюме + экспорт и скачивание
    TXT/DOCX);
  - **настройки**, **онбординг** (баннер «Готовность» на основе `doctor`,
    авто-скачивание моделей, HF-токен как секрет, мастер первого запуска) и
    **тёмная/светлая/авто тема**.
- **CLI на [Typer](https://typer.tiangolo.com/)** (`audio-transcriber
  transcribe`) — для скриптов и автоматизации, с полным набором параметров.
- **TUI** на [Textual](https://textual.textualize.io/): очередь, живой
  прогресс, поиск по стенограмме. Сохраняется для любителей терминала, но
  больше не развивается и не является основным путём.
- **Распознавание речи** полностью локально, на выбор:
  - [`faster-whisper`](https://github.com/SYSTRAN/faster-whisper) — CUDA/CPU
    через PyTorch (по умолчанию);
  - [`whisper.cpp`](https://github.com/ggml-org/whisper.cpp) — GPU через
    **Vulkan**, поэтому работает и на AMD-картах **без ROCm**. Длинные записи
    режутся на куски ~30 с с перекрытием ~2 с, а затем склеиваются с
    дедупликацией — это устраняет потерю текста и «шаблонные» галлюцинации.
- **Определение говорящих** (диаризация) через
  [pyannote.audio](https://github.com/pyannote/pyannote-audio); можно
  использовать локальную копию модели и работать полностью офлайн.
- **Перекрытия речи**: если говорили несколько человек одновременно, в реплике
  указываются **все** говорящие («Имя1 + Имя2»).
- **Уверенность говорящего** (`?`): реплика помечается, когда привязка к
  говорящему ненадёжна. Легенда меток: `⚠ низкая уверенность`,
  `⇄ наложение речи`, `? говорящий под вопросом`.
- **LLM-постобработка** локальной моделью через
  [llama.cpp](https://github.com/ggml-org/llama.cpp) (Vulkan):
  правка терминов по глоссарию (и экспериментальное, по умолчанию выключенное
  определение имён участников); при нехватке видеопамяти клиент сам деградирует
  до CPU.
- **Шумоподавление (денойз)** перед распознаванием и диаризацией на
  [DeepFilterNet](https://github.com/Rikorose/DeepFilterNet) — включено по
  умолчанию; если движок не установлен, этап мягко пропускается.
- **Глоссарий терминов**: локальная SQLite-база (`glossary.db`) с источниками и
  терминами (включение/выключение источников и записей, импорт TXT/CSV), а
  также совместимые текстовые файлы, явные пары «как слышит ASR = канон»,
  односложные и фразовые термины и авто-сбор предложений о новых терминах.
- **Склейка реплик в предложения**: подряд идущие короткие сегменты одного
  говорящего объединяются, чтобы текст читался как связная речь.
- **Качество стенограммы**: разметка уверенности распознавания (`avg_logprob`)
  с пометкой низкоуверенных реплик (`⚠`), устранение «зацикливаний» Whisper,
  безопасная нормализация текста, пометка зон наложения речи (`⇄`) и очистка
  неречевых артефактов (скобочные пометки, «голые» шумовые слова, шаблонные
  галлюцинации).
- **Протокол**: резюме и итоговые документы формируются **по кнопке** (в вебе и
  TUI) по актуальной стенограмме; в CLI по умолчанию поведение прежнее.
- **Экспорт** стенограммы в TXT, DOCX, JSON и SRT с разметкой говорящих.
- Возможность задать **пользовательские имена говорящих** вместо
  `SPEAKER_00`, `SPEAKER_01`, ...
- **Автоисправление опечаток** ASR по морфологическому словарю
  (`--enable-correction`, по умолчанию выключено).
- **Постадийный кэш** дорогих этапов (денойз/ASR/диаризация): повторный запуск
  на том же файле с теми же параметрами не пересчитывает их, а прогон, упавший
  на диаризации, при повторе переиспользует готовый ASR (возобновление после сбоя).
- **Самопроверка окружения** командой `audio-transcriber doctor`: версия Python,
  зависимости, бинарники и модели, GPU Vulkan (через `vulkaninfo` — не все
  сборки `whisper-cli` умеют `--list-devices`), `config.env`, токен,
  доступность каталогов результатов и кэша.

## Требования

- Python **3.14+**.
- [uv](https://docs.astral.sh/uv/) для управления зависимостями и окружением.
- **Оборудование (гибридная схема, выбрать одно):**
  - **NVIDIA + CUDA** — быстрый инференс через `faster-whisper`/PyTorch
    (на Windows/Linux CUDA-сборка `torch` ставится автоматически, см.
    [«Выбор устройства»](#выбор-устройства-cpugpu));
  - **AMD (или любой GPU) без ROCm** — `whisper.cpp` + `llama.cpp` через
    **Vulkan**; сборки `torch` при этом не нужны (подойдёт CPU-сборка);
  - **CPU** — как запасной вариант в любом случае (медленнее).
- **Локальные модели** (скачиваются один раз, дальше всё офлайн):
  - диаризация — модель pyannote;
  - распознавание для `whisper.cpp` — ggml-модель (`whisper-models/`);
  - LLM — GGUF-модель (`llama-models/`).
- **Шумоподавление (опционально)** — пакет
  [DeepFilterNet](https://github.com/Rikorose/DeepFilterNet); собирается из
  исходников (нужен Rust), см. раздел
  [«Шумоподавление (денойз)»](#шумоподавление-денойз). Без него конвейер
  работает как раньше.
- Аккаунт на [huggingface.co](https://huggingface.co) и токен доступа **нужны
  только** для первой загрузки модели диаризации. Если указана локальная
  копия модели (`PYANNOTE_LOCAL_MODEL`), токен и сеть не требуются — см.
  [«Токен доступа для диаризации»](#токен-доступа-для-диаризации).



## Установка

```bash
git clone <url-репозитория>
cd PyAudioTranscriptor
uv sync
```

`uv sync` создаст виртуальное окружение `.venv`, установит зависимости из
`pyproject.toml`/`uv.lock`, саму утилиту в редактируемом режиме и
dev-инструменты (`pytest`, `ruff`, `mypy`).

На Windows/Linux в зависимости уже включена CUDA-сборка PyTorch (см. раздел
[«Выбор устройства (CPU/GPU)»](#выбор-устройства-cpugpu)), поэтому `uv sync`
скачивает несколько гигабайт (в основном сам `torch` с бинарниками CUDA) —
это нормально и происходит один раз. Если CUDA не нужна (например, при работе
через Vulkan на AMD), достаточно CPU-сборки `torch`; запуск тогда идёт
напрямую через `.venv/bin/audio-transcriber` — так делает `run.sh`.

### Бинарники и модели для GPU-Vulkan

`faster-whisper` работает через PyTorch, а `whisper.cpp` и `llama.cpp` — это
отдельные нативные сборки. Для гибридной схемы (AMD/любой GPU через Vulkan)
рядом с проектом удобно держать:

```
whisper-native/   # whisper-cli + разделяемые библиотеки (.so) whisper.cpp
llama-native/     # llama-server + библиотеки llama.cpp (libggml-vulkan.so, ...)
whisper-models/   # ggml-модели для whisper.cpp (напр. ggml-large-v3-turbo.bin)
llama-models/     # GGUF-модели для LLM (напр. Qwen2.5-7B-Instruct Q4_K_M)
```

Важно: в сборках llama.cpp нового поколения бэкенды (`.so`) грузятся
динамически и ищутся **рядом с бинарником**, поэтому бинарник и библиотеки
должны лежать в одном каталоге. Пути к бинарникам, каталогам с библиотеками и
моделям задаются в `config.env` (`WHISPER_CPP_*`, `LLM_*`).

## Быстрый запуск (без ручной установки и параметров в командной строке)

В репозитории есть готовые скрипты-обёртки: `run.sh` (Linux/macOS) и
`run.ps1` / `run.bat` (Windows) — они не требуют команд `uv` и параметров в
командной строке. Скрипты сами устанавливают `uv`, если его нет, и запускают
транскрибацию с параметрами, которые вы один раз укажете в файле
`config.env`.

**Настройка (один раз):**

1. Скопируйте `config.example.env` в `config.env`.
2. Откройте `config.env` и укажите токен Hugging Face (см. раздел
   [«Токен доступа для диаризации»](#токен-доступа-для-диаризации)) либо путь
   к локальной модели (`PYANNOTE_LOCAL_MODEL`), а также модель, язык,
   бэкенд распознавания, пути к бинарникам/моделям Vulkan и параметры LLM.

**Запуск:**

- Linux/macOS:
  ```bash
  ./run.sh path/to/call.mp3
  ```
- Windows (PowerShell):
  ```powershell
  .\run.ps1 path\to\call.mp3
  ```
- Windows (без терминала): перетащите аудиофайл мышью на `run.bat`.

`run.sh` читает `config.env` и сам пробрасывает нужные параметры в CLI:
`ASR_BACKEND`, `WHISPER_CPP_MODEL/BINARY/LIB_PATH`, `LLM_*` (модель, бинарник,
контекст, CPU/GPU, извлечение имён, предложения терминов) и `GLOSSARY_PATH`.
`run.ps1` / `run.bat` синхронизированы с `run.sh`: сами разбирают `config.env`
(без bash), снимают кавычки и поддерживают те же переменные.

Если позже понадобится изменить модель, язык, формат экспорта или другие
параметры — не нужно ничего вспоминать, просто откройте `config.env` и
поменяйте нужное значение. Полный список переменных — в разделе
[«Конфигурация `config.env`»](#конфигурация-configenv).

## Веб-интерфейс

Основной способ работы — локальный веб-интерфейс: сервер слушает только
`127.0.0.1`, наружу ничего не выставляется, а работать можно из браузера на
Windows, macOS и Linux. Нативный стек (распознавание, диаризация, LLM) при
этом всё равно требует бинарников и моделей, собранных под конкретную ОС.

### Установка

Веб-зависимости (`FastAPI`, `uvicorn`, `python-multipart`) вынесены в
отдельный extra `web`:

```bash
uv sync
uv pip install --python .venv/bin/python ".[web]"
```

### Запуск

```bash
uv run audio-transcriber web
# или: .venv/bin/audio-transcriber web
```

По умолчанию сервер занимает `http://127.0.0.1:8765/` и автоматически
открывает браузер. Если порт `8765` занят, а `--port` **не задан явно**,
подбирается ближайший свободный порт (`8766`, `8767`, … до `8765+50`), и
фактический адрес печатается в консоли и открывается в браузере. Если порт
задан явно через `--port` и он занят — команда завершается понятной ошибкой,
не подменяя порт молча.

| Флаг | Назначение |
|---|---|
| `--host` | Адрес прослушивания (по умолчанию `127.0.0.1`). |
| `--port` | Порт сервера. Если не задан — `8765`, при занятости подбирается свободный. |
| `--no-browser` | Не открывать браузер автоматически. |
| `--reload` | Автоперезапуск при изменении кода (для разработки). |

Остановить сервер — `Ctrl+C` в терминале. Фактический адрес доступен в
`GET /api/health` (поля `host` и `port`).

**Готовые ярлыки** (по аналогии с `run.sh` / `run.ps1`):

- Linux/macOS: `./web.sh` — из терминала или двойным щелчком;
- Windows: `web.bat` (двойной щелчок) или `.\web.ps1` из PowerShell.

Они сами поднимают `audio-transcriber web` и подсказывают
«Ctrl+C — остановить». Адрес и фактический порт печатает сама команда, поэтому
ярлык не дублирует URL (при автоподборе порта он может отличаться от `8765`).
Если веб-зависимости не установлены, скрипт подскажет команду установки.

### Возможности

- **Очередь задач**: список файлов в каталоге загрузок, загрузка и удаление
  файлов, выбор и постановка в очередь. **Число говорящих** задаётся при
  постановке в очередь (по умолчанию «авто»).
- **Мягкое удаление задач**: «Удалить» скрывает задачу из списка, сохраняя
  результат и образцы; тумблер **«Показать удалённые»** показывает удалённые
  (с бейджем «Удалено»), их можно **восстановить** или **удалить навсегда**
  (с подтверждением). Активную задачу удалить нельзя — сначала остановите её.
- **Живой прогресс** по стадиям (денойз → распознавание → диаризация →
  объединение → очистка → экспорт) через Server-Sent Events, с
  **длительностями каждой стадии и общим временем обработки**.
- **Стенограмма**: поиск и пометки, **прослушивание фрагмента прямо из
  реплики** (▶).
- **Правка говорящих**: переименование и объединение спикеров прямо в
  стенограмме.
- **«Применить имена»**: сопоставление говорящих с именами по образцам голоса
  из библиотеки и по явно заданным образцам.
- **Библиотека голосов**: загрузка, прослушивание, переименование и удаление
  образцов, сохранение образца говорящего из задачи.
- **Глоссарий**: управление SQLite-БД терминов и её источниками — источники с
  галочками, добавление/удаление записей, импорт TXT/CSV.
- **«Сформировать протокол»**: резюме по актуальной стенограмме, экспорт и
  скачивание TXT/DOCX.
- **Настройки**: глоссарий, каталог голосов, форматы экспорта, LLM-резюме,
  денойз, разметка перекрытий и другое.
- **Онбординг**: баннер «Готовность» на основе `doctor`, авто-скачивание
  моделей, токен Hugging Face как секрет и мастер первого запуска.
- **Тема**: тёмная, светлая или авто.
- **Прослушивание** исходного аудио (HTTP Range) и образцов говорящих.

### Ограничения

- Сервер слушает только `127.0.0.1` и не имеет аутентификации — он рассчитан
  на работу на одном компьютере.
- Фоновая очередь обрабатывает задачи **одним воркером** (последовательно).

## Интерактивный интерфейс (TUI)

TUI на [Textual](https://textual.textualize.io/) сохранён для тех, кто
предпочитает терминал, но **больше не развивается** и не является основным
путём: новые возможности появляются в веб-интерфейсе. Это полноэкранный
интерфейс (htop-стиль): выбрать файлы в дереве, поставить несколько записей в
очередь и следить за живым прогрессом по этапам прямо во время обработки.

- Linux/macOS: ярлык-скрипт `launch-tui.sh` (можно запускать двойным щелчком).
- Либо вручную:

  ```bash
  uv run audio-transcriber tui
  # или: .venv/bin/audio-transcriber tui
  ```

Настройки TUI берёт из того же `config.env`; LLM-клиент создаётся один раз на
всю очередь и гарантированно закрывается после её обработки. Шумоподавление
включается/выключается переключателем **«Шумоподавление (денойз)»** в простом
режиме настроек. В **продвинутом режиме** есть поле **«Образцы голоса»**
(формат `Имя=путь.wav,Имя2=путь2.wav`) и **«Порог голоса»** для
enrollment-диаризации.

**Поиск по стенограмме.** Над таблицей результатов есть поле поиска: нажмите
`/` или `Ctrl+F`, чтобы перейти в него, и введите запрос. Совпадения
подсвечиваются фильтрацией строк, рядом показывается число найденных реплик.
Поиск не зависит от регистра и идёт по тексту реплик и имени говорящего;
несколько слов в запросе означают «И» — строка остаётся, только если
присутствуют **все** слова (например, `иван привет`). `Esc` очищает фильтр и
возвращает все реплики.

**Уведомления о завершении.** По окончании очереди TUI отправляет
десктоп-уведомление (`notify-send`) об успехе или об ошибках. Отключается
переключателем **«Уведомления»** (и переменной `NOTIFICATIONS=false`); если
утилиты `notify-send` нет, уведомление тихо пропускается.

### Повышение точности распознавания

`faster-whisper` иногда заменяет редкие слова на похожие по звучанию —
например, вместо «взаимопонимания» может получиться «взаимоприимания».

1. **`--enable-correction`** — автоисправление опечаток ASR. Для неизвестных
   словоформ подбирается ближайшая известная форма русского языка
   (морфологический словарь OpenCorpora через `pymorphy3`). Пользовательский
   словарь терминов не нужен. По умолчанию выключено.

   Правки намеренно консервативны: допускается не более **одной правки
   символа** на слово, порог сходства высокий (`0.93`), а слова с латиницей
   (`login`, `reloadConfig`) не трогаются вовсе. Так тех-заимствования
   («залогинился», «залочился», «перелагирование») не «исправляются» на
   похожие русские слова.

   Важно: исправляются **только** слова, которые морфологический анализатор
   не считает известными формами. Обычные слова и склонения («есть»,
   «представителем», «гражданского») не трогаются. Каждая замена пишется в лог:
   `Автоисправление: «Конфиденциальнасть» → «Конфиденциальность»`.

   ```bash
   uv run audio-transcriber transcribe recording.mp3 --enable-correction
   ```

   В `config.env`:

   ```
   ENABLE_CORRECTION=true
   CORRECTION_MIN_WORD_LENGTH=6
   CORRECTION_MIN_SIMILARITY=0.93
   CORRECTION_MAX_CANDIDATES=8000
   ```

2. **`--hotwords`** / **`--initial-prompt`** — короткие подсказки ASR во время
   распознавания (имена и 5–15 критичных терминов). Ограничены ~100 токенами
   Whisper; для больших списков не подходят.

Также по умолчанию включены отсечение тишины/не-речи (VAD) и уточнение границ
сегментов по словам.

#### Выбор модели: `medium` / `large-v3-turbo` / `large-v3`

По умолчанию используется `large-v3-turbo` — облегчённая версия `large-v3` от
OpenAI (меньше слоёв в декодере). На практике она распознаёт как минимум не
хуже `medium`, а часто точнее, и при этом работает быстрее — хороший вариант
по умолчанию для большинства видеокарт.

Полноразмерная `large-v3` точнее всего, но требует заметно больше видеопамяти
и работает медленнее — на слабых/старых GPU ей может не хватить видеопамяти
(ошибка `CUDA failed with error out of memory`), тогда придётся использовать
`--device cpu`, что значительно медленнее. Если видеокарта современная и с
большим объёмом памяти, стоит попробовать `--model large-v3` для максимальной
точности.

Полностью исключить ошибки распознавания невозможно — при работе с
материалами, где точность критична (например, для суда), финальный текст
рекомендуется дополнительно проверять на слух.

### Чанкинг длинных записей (whisper.cpp)

У whisper.cpp есть особенность: внутри одного запуска он накапливает текстовый
контекст между своими 30-секундными окнами, и на длинной записи это приводит к
потере речи и «шаблонным» галлюцинациям. Поэтому на файлах длиннее
`WHISPER_CPP_CHUNK_SECONDS` движок режет запись на куски ~30 с с перекрытием
~2 с, распознаёт каждый кусок **отдельным** вызовом `whisper-cli`, сдвигает
таймкоды и склеивает результат, дедуплицируя реплики из области перекрытия.
Границы кусков подбираются в тихие точки по энергии сигнала, чтобы не разрезать
слово.

- `WHISPER_CPP_CHUNK_SECONDS` — целевая длина куска, секунды (по умолчанию
  `30`; `0` — выключить чанкинг и вернуть прежнее поведение «один вызов на весь
  файл»).
- `WHISPER_CPP_CHUNK_OVERLAP` — перекрытие соседних кусков, секунды (по
  умолчанию `2`; больше — надёжнее на стыках, но чуть медленнее).

Если входной файл уже подходит под whisper.cpp напрямую (16 кГц моно PCM WAV —
именно такой отдаёт шумоподавление), лишних перекодирований не делается.

### Глоссарий терминов

Термины для правки ASR ведутся в локальной **SQLite-базе** `glossary.db` (путь
переопределяется переменной `GLOSSARY_DB`): у каждой записи есть источник, а
источники и записи можно включать и выключать. Управлять базой удобно из
веб-интерфейса (источники с галочками, добавление/удаление, импорт TXT/CSV)
или CLI-подкомандой `glossary`:

```bash
uv run audio-transcriber glossary import glossary.txt   # импорт TXT/CSV в БД
uv run audio-transcriber glossary list                   # список записей
uv run audio-transcriber glossary add "АИБ = ОИБ"        # пара «ошибочная форма = канон»
uv run audio-transcriber glossary sources                # источники и число записей
uv run audio-transcriber glossary enable|disable <ист.>  # включить/выключить источник
uv run audio-transcriber glossary remove <ист.|id>       # удалить источник или запись
```

При первом обращении база наполняется из прежних файлов `GLOSSARY_PATH`
(авто-миграция), поэтому старые глоссарии продолжают работать без изменений.

Помимо базы поддерживаются **обычные текстовые файлы** — совместимый формат и
источник для импорта: один термин или пара в строке, строки, начинающиеся с
`#`, и пустые строки игнорируются. Термин может быть как одним словом (`ОИБ`,
`транскрибер`), так и фразой (`информационная безопасность`).

- **Обычные термины** приводятся к канону детерминированным матчером: он
  учитывает регистр и склонения, точные слова не меняет, а короткие
  аббревиатуры правит только при единственном кандидате.
- **Явные пары** `АИБ = ОИБ` («как слышит ASR = канон») применяются всегда и
  приоритетнее нечёткого сопоставления — надёжный способ гарантировать замену.
- **Несколько файлов** объединяются: `--glossary a.txt --glossary b.txt` или
  `GLOSSARY_PATH=a.txt,b.txt` (разделитель — запятая или `os.pathsep`).

Пример запуска:

```bash
uv run audio-transcriber transcribe call.mp3 --glossary glossary.txt
```

Шаблон формата — `glossary.example.txt`. Если включён `--llm-suggest-terms`
(или `LLM_SUGGEST_TERMS=true`), рядом с первым глоссарием появится файл
`<имя>.suggested.txt` с терминами-кандидатами (частота и источник) — их можно
вручную перенести в глоссарий.

### LLM-постобработка (имена и термины)

Локальная LLM через `llama.cpp` (`llama-server`, GPU через Vulkan или CPU)
решает две задачи:

1. **Имена участников (ЭКСПЕРИМЕНТАЛЬНО, по умолчанию выключено).**
   Модель читает стенограмму с метками «Спикер N» и возвращает имя только при
   явном основании в тексте; имя, которого нет в стенограмме, не применяется
   (защита от галлюцинаций). Функция пока нестабильна — включайте осознанно
   (`--llm-names` или `LLM_EXTRACT_NAMES=true`).
2. **Правка терминов.** Поверх детерминированного матчера LLM дополнительно
   находит спорные ASR-опечатки терминов, но применить разрешено только замену
   на канонический термин из глоссария.

Включается флагом `--llm` и указанием модели:

```bash
uv run audio-transcriber transcribe call.mp3 \
  --asr-backend whisper-cpp \
  --whisper-cpp-model whisper-models/ggml-large-v3-turbo.bin \
  --llm --llm-model llama-models/qwen2.5-7b-instruct-q4_k_m.gguf \
  --glossary glossary.txt
```

В `config.env` используются `LLM_ENABLED`, `LLM_MODEL`, `LLM_BINARY`,
`LLM_LIB_PATH`, `LLM_GPU`, `LLM_CONTEXT`, `LLM_REQUEST_TIMEOUT`,
`LLM_EXTRACT_NAMES`, `LLM_SUGGEST_TERMS` и `GLOSSARY_PATH`. При нехватке
видеопамяти клиент деградирует сам: частичная выгрузка слоёв на GPU, затем
чистый CPU.

### Шумоподавление (денойз)

Перед распознаванием и диаризацией запись можно очистить от фонового шума
нейросетевой моделью [DeepFilterNet](https://github.com/Rikorose/DeepFilterNet)
(DeepFilterNet3). Этап включён по умолчанию и стоит первым в конвейере:
**один и тот же очищенный файл** получают и ASR, и диаризация, поэтому их
временные метки согласованы, а объединение (`merge`) остаётся корректным.

Денойз декодирует исходник один раз и отдаёт диаризации уже готовый моно
waveform 16 кГц (в памяти), поэтому повторного чтения того же аудио с диска
не происходит. На длинных записях это экономит заметное время и память:
например, для 30-минутной фонограммы одно декодирование 16-кГц WAV — это
порядка секунды и ~115 МБ `float32`.

Как выключить:

- CLI: `--no-denoise`;
- `config.env`: `DENOISE=false` (тогда `run.sh` передаст `--no-denoise`);
- TUI: переключатель **«Шумоподавление (денойз)»**.

#### Установка

DeepFilterNet объявляет зависимость `numpy<2`, а проект использует `numpy 2.x`
(для Python 3.14 колёс под `numpy 1.26` нет). Поэтому пакет ставится **вручную
без зависимостей** — так основной `numpy`/`torch` не откатываются. Сборка
`libDF` идёт на Rust, нужен установленный `cargo`/`rustc`:

```bash
# установить Rust, если его нет: https://rustup.rs
uv pip install --python .venv/bin/python --no-deps \
    deepfilternet deepfilterlib appdirs loguru
```

Проверка:

```bash
.venv/bin/python -c "from df import enhance, init_df; print('DeepFilterNet OK')"
```

При первом запуске модель (~9 МБ) скачивается в кэш
`~/.cache/DeepFilterNet/DeepFilterNet3`; дальше инференс полностью локальный и
офлайн. Если пакет не установлен или модель недоступна, этап **мягко
пропускается** с предупреждением в лог — конвейер продолжает работать на
исходном аудио (то же и при сбое декодирования файла).

> В `pyproject.toml` DeepFilterNet объявлен как необязательный extras
> `denoise` (с маркером `python_version < '3.14'`), чтобы он не ломал общий
> резолв зависимостей. На Python 3.14 используйте команду выше. Учтите, что
> `uv sync` синхронизирует окружение строго по `uv.lock` и может удалить
> вручную поставленные пакеты — при необходимости просто повторите установку.

#### Производительность

DeepFilterNet работает на 48 кГц моно; конвейер — на 16 кГц. Полный цикл:
декодирование (PyAV) → 48 кГц → модель → ресемплинг в 16 кГц → временный WAV.
Замер на CPU (без GPU), 90-секундный фрагмент телефонного разговора:
чистый инференс **≈ 3.2 с** (RTF ≈ `0.035`, то есть ~28× быстрее реального
времени); с учётом декодирования/ресемплинга/записи и однократной загрузки
модели — **≈ 4.3 с** (RTF ≈ `0.048`).

Технические детали: аудио читается через PyAV (а не `torchaudio.load`,
который зависит от `torchcodec`), а совместимость `df.io` с torchaudio ≥ 2.9
(удалённый `torchaudio.backend.common`) обеспечивается небольшой заглушкой в
`denoising/deepfilter.py` — `site-packages` не изменяется.

Денойз работает **потоково, чанками** (по умолчанию 30 с, перекрытие 0.5 с):
файл не грузится целиком в 48 кГц, а декодируется кадрами, и каждый готовый
чанк сразу прогоняется через модель. Соседние чанки склеиваются
кроссфейд-overlap-add (без щелчков, пропусков и дублей), а ресемплинг 48 → 16 кГц
идёт одним постоянным ресемплером, поэтому фильтр непрерывен на стыках. В памяти
живут только текущий чанк (~5.5 МБ), хвост перекрытия и итоговый 16-кГц waveform
(~230 МБ/час) — можно передавать размер чанка параметром `chunk_seconds`.
Пиковая память стадии для часовой записи — порядка **0.2–0.3 ГБ** вместо
~1.4–2 ГБ при загрузке всего 48-кГц буфера и его копий.

### Качество стенограммы: уверенность, повторы, перекрытия

Несколько независимых механизмов повышают читаемость и достоверность стенограммы.

**1. Разметка уверенности распознавания (`avg_logprob`).** Для каждой реплики
сохраняется средняя логвероятность ASR. Реплики ниже порога
`LOW_CONFIDENCE_THRESHOLD` (по умолчанию `-1.0`; логвероятности `<= 0`; более
отрицательное значение — меньше пометок) помечаются:

- TXT/DOCX — суффикс `⚠ [низкая уверенность]`;
- JSON — поля `avg_logprob` и `low_confidence`.

`faster-whisper` отдаёт уверенность всегда; `whisper.cpp` — только в полном
JSON (`-ojf`), который используется автоматически, а уверенность считается как
среднее `ln(p)` по «речевым» токенам. Если движок вероятностей не даёт, реплика
не помечается (мягкая деградация). Отключение — `--low-confidence-threshold=-10`
(или любое очень отрицательное значение).

**2. Устранение «зацикливаний» Whisper** (`COLLAPSE_REPEATS=true`, включено).
Подряд идущие одинаковые/почти одинаковые реплики («Продолжение следует» ×N,
титры редактора/корректора субтитров и т.п.) схлопываются в одну. Короткая
осмысленная речь («да, да») сохраняется: схлопываются реплики не короче
`REPEAT_MIN_WORDS` слов (известные фразы-заглушки — исключение), «почти
одинаковые» — по порогу `REPEAT_SIMILARITY`. Отключение — `--no-collapse-repeats`.

**3. Безопасная нормализация текста** (`NORMALIZE_TEXT=true`, включено).
Схлопываются повторная пунктуация (`!!!` → `!`), лишние многоточия (`..` → `.`,
`......` → `...`), двойные пробелы и пробелы перед знаками; числа/даты — только
элементарные случаи (пробелы внутри десятичной дроби, вокруг `:` и `%`). Слова
не переписываются, текст без отклонений не меняется. Отключение —
`--no-normalize`.

**4. Пометка наложения речи** (`MARK_OVERLAP=true`, включено). Реплики,
попавшие в зоны, где одновременно говорили `>= 2` человек, помечаются:
TXT/DOCX — `[наложение речи]`, JSON — `overlap: true`. Если зоны несут
участников (обычная, не эксклюзивная разметка pyannote), в реплике указываются
**все** говорившие — «Имя1 + Имя2». Если данных о перекрытиях нет, пометок не
будет и конвейер не упадёт. Отключение — `--no-overlap`.

**5. Уверенность говорящего (`?`).** Для реплики сохраняется
`speaker_confidence` — доля её интервала, покрытая основным говорящим. Если
привязка реплики к говорящему ненадёжна (ниже порога `0.5`), реплика
помечается `? [говорящий под вопросом]`. Это независимо и от уверенности
распознавания, и от наложения.

**6. Очистка неречевых артефактов** (`CLEAN_ARTIFACTS=true`, включено). Из
реплик удаляются пометки, которых не было в речи: скобочные (`[АПЛОДИСМЕНТЫ]`,
`(смех)`) и музыкальные символы (`♪`), «голые» шумовые слова (серии
повторяющегося «АПЛОДИСМЕНТЫ»), **шаблонные галлюцинации** Whisper
(«Продолжение следует», «Добро пожаловать в Казахстан», «Субтитры…», «Спасибо
за просмотр» и т.п.) и реплики с «аномально малым текстом на длинном
интервале». Обычный текст не изменяется. Отключение — `--no-clean`.

**Легенда меток** (в TXT/DOCX, колонке «Метки» в TUI и в стенограмме веба):
`⚠ низкая уверенность`, `⇄ наложение речи`, `? говорящий под вопросом`.

Все параметры доступны через CLI, `config.env`, настройки веб-интерфейса и
переключатели TUI (простого режима). Значения по умолчанию — в
`config.example.env`.

### Имена участников по образцам голоса (enrollment-диаризация)

Вместо ручного сопоставления «индекс → имя» (`--speaker-name 0=Иван`) можно
дать движку короткие образцы голоса участников — он сам сопоставит
диаризованных говорящих с именами по голосу:

```bash
uv run audio-transcriber transcribe records/call.mp3 \
  --speaker-reference Иван=/home/me/voice_ivan.wav \
  --speaker-reference Мария=/home/me/voice_maria.wav \
  --enrollment-min-similarity 0.6
```

В `config.env` то же самое задаётся через `SPEAKER_REFERENCES` (через запятую):

```env
SPEAKER_REFERENCES=Иван=/home/me/voice_ivan.wav,Мария=/home/me/voice_maria.wav
ENROLLMENT_MIN_SIMILARITY=0.6
```

**Как это работает.** Для каждого образца и каждого говорящего считается
speaker-эмбеддинг (WeSpeakerResNet34 из локальной модели диаризации; окно ~5 c,
16 кГц моно). У образцов усредняются окна (можно дать несколько клипов на одно
имя), у говорящего — эмбеддинги его самых длинных сегментов (до трёх). Затем
строится матрица косинусного сходства «говорящий × имя» и выполняется жадный
мэтчинг один-к-одному. Имя присваивается, только если сходство не ниже
`ENROLLMENT_MIN_SIMILARITY` (по умолчанию `0.6`); иначе говорящий остаётся
«Спикер N» — лучше не назвать, чем подписать реплики чужим голосом. Матрица
сходства пишется в лог на уровне `DEBUG` (`--verbose`).

**Приоритет имён.** Если enrollment-сопоставление сработало, имя по голосу
приоритетнее `SPEAKER_NAMES`/`--speaker-name` (переименования по индексу).
Совпавшие по голосу говорящие получают enrollment-имена; остальные — прежние
метки (`--speaker-name` либо «Спикер N»). Если образцы не заданы или матчинг не
дал уверенных совпадений, поведение полностью прежнее.

**Мягкая деградация.** При отсутствии образцов, недоступности модели
эмбеддингов (например, нет локальной `PYANNOTE_LOCAL_MODEL`) или ошибке чтения
файла этап лишь пишет предупреждение в лог и не меняет имена — конвейер не
падает. Локальная модель используется офлайн; сеть не требуется.

**Подготовка эталона (#29).** Качество образца критично: тишина и шум
«размывают» эмбеддинг, а несогласованная обработка образца и тестовых окон
даёт domain mismatch. При `REFERENCE_PREPARE=true` (по умолчанию) образец
приводится к единому виду на примитивах проекта (без новых зависимостей):
VAD-обрезка тишины с запасом ~0.1 с, ограничение длительности чистой речи
3–10 с (`ENROLLMENT_MIN_SAMPLE_SECONDS`/`ENROLLMENT_MAX_SAMPLE_SECONDS`) и
лёгкая RMS-нормализация до `REFERENCE_TARGET_DBFS` (−30 dBFS) в режиме
`increase_only` (тихие усиливаются, громкие не глушатся; усиление ограничено).
Та же обработка применяется и к эталонам, и к окнам говорящего. Подготовка
выполняется при сохранении образца в библиотеку (загрузка файла и «В
библиотеку» из задачи/варианта) — метрики и предупреждения (`too_short`,
`clipped`, `low_energy`, `mostly_non_speech`) возвращаются в API и показываются
в веб-интерфейсе. Денойз к эталону отдельно не применяется: он искажает
speaker-признаки. Параметры — в `config.env` (см. `config.example.env`).

> **Про качество образцов.** Берите клип ≥ 3–5 c чистой речи одного человека,
> без музыки и наложения других голосов. Слишком короткие (< ~1 c) и шумные
> образцы дают ненадёжный эмбеддинг. Порог `0.6` — разумная отправная точка;
> если имена путаются, поднимите его, если не присваиваются — понизьте.

### Токен доступа для диаризации

Модель диаризации распространяется через Hugging Face и требует один раз
зарегистрироваться, принять условия использования и получить токен доступа.
Никакой оплаты это не требует — аккаунт и токен полностью бесплатны:

1. Зарегистрируйтесь на [huggingface.co](https://huggingface.co/join) (если
   аккаунта ещё нет).
2. Примите условия [`pyannote/speaker-diarization-community-1`](https://hf.co/pyannote/speaker-diarization-community-1)
   — откройте страницу модели и нажмите «Agree and access repository».
3. Создайте токен на [hf.co/settings/tokens](https://hf.co/settings/tokens)
   (достаточно прав `Read`).
4. Передайте токен утилите одним из способов:
   - через параметр `--hf-token <токен>`;
   - через переменную окружения `HF_TOKEN` (также поддерживается
     `HUGGING_FACE_HUB_TOKEN`). В PowerShell для текущей сессии:

     ```powershell
     $env:HF_TOKEN = "hf_xxx..."
     ```

Сама диаризация после загрузки модели выполняется полностью локально —
токен нужен только для первого скачивания весов модели, дальнейшие запуски
используют уже сохранённый локальный кэш Hugging Face.

Если сеть и токен нежелательны, укажите заранее скачанную локальную копию
модели (`--pyannote-local-model /путь/к/модели` или `PYANNOTE_LOCAL_MODEL` в
`config.env`) — тогда модель грузится с диска, а токен и интернет не нужны.

### Выбор устройства (CPU/GPU)

Утилита работает по гибридной схеме: распознавание — либо через
`faster-whisper`/PyTorch (CUDA/CPU), либо через `whisper.cpp`/Vulkan (для
AMD-карт без ROCm, а также любых GPU с драйвером Vulkan). Диаризация
выполняется на CPU или CUDA, LLM — на Vulkan/CPU через `llama.cpp`.

- **`--asr-backend faster-whisper`** (по умолчанию): PyTorch ускоряет
  вычисления через CUDA, при её отсутствии автоматически используется CPU.
  Устройство задаётся флагом `--device auto|cuda|cpu`.
- **`--asr-backend whisper-cpp`**: распознавание идёт в нативном `whisper-cli`
  через Vulkan, при этом `--device` управляет только диаризацией (в этой схеме
  pyannote всегда считается на CPU — у него нет Vulkan-бэкенда).

```bash
uv run audio-transcriber transcribe records/call.mp3 --device cuda
```

На macOS CUDA-сборок PyTorch не существует — там `uv sync` ставит обычный
CPU-индекс; нативные сборки `whisper.cpp`/`llama.cpp` при этом можно собрать
под Metal/Vulkan отдельно.

`pyproject.toml` уже настроен так, чтобы `uv sync` на Windows/Linux
устанавливал именно CUDA-сборку PyTorch (`[tool.uv.sources]` /
`[[tool.uv.index]]`), а не CPU-only пакет из обычного PyPI — иначе
`torch.cuda.is_available()` всегда возвращает `False`, даже если GPU и
драйверы в порядке. На macOS, где CUDA-сборок PyTorch не существует,
используется обычный CPU-индекс.

Версии `torch`/`torchaudio` закреплены (`torch<2.13`, `torchaudio<2.12`) на
последней сборке с CUDA 12.6 — это осознанное ограничение: начиная со
следующих версий PyTorch перестал выпускать сборки под CUDA 12.6, а именно
эта ветка CUDA — последняя, поддерживающая GPU архитектур Maxwell, Pascal и
Volta (например, GTX 900/1000-й серии). На более новых картах (RTX 20xx и
новее) можно ослабить это ограничение и использовать более новую CUDA-ветку
(`cu128`, `cu130` и т.д. — см. [актуальный список](https://download.pytorch.org/whl/)).

Проверить, что PyTorch действительно видит GPU, можно так:

```bash
uv run python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

Если `--device cuda` всё равно завершается ошибкой «CUDA не найдена», хотя
видеокарта NVIDIA есть, проверьте:

- установлены ли актуальные драйверы NVIDIA (`nvidia-smi` должен показывать GPU);
- не установился ли CPU-only `torch` (команда выше должна вывести `True`,
  а версия должна содержать суффикс `+cuXXX`, например `2.12.1+cu126`, а не
  `+cpu`). Если суффикс `+cpu` — выполните `uv sync` заново после проверки
  секции `[tool.uv.sources]` в `pyproject.toml`;
- достаточно ли новая архитектура GPU для выбранной ветки CUDA (см. выше про
  Pascal/Maxwell/Volta и CUDA 12.6).

### Запуск на macOS

Проект рассчитан на Linux, Windows и macOS, но на маке набор доступных
ускорений и нативных библиотек другой:

- **Python 3.14+** ставится через `uv`; `pyproject.toml` для
  `sys_platform == 'darwin'` подтягивает CPU-сборку `torch`/`torchaudio`
  (CUDA на macOS не существует).
- **Распознавание**: работает `--asr-backend faster-whisper` на CPU
  (медленнее, чем на CUDA; Metal-ускорения у CTranslate2 нет).
- **Гибрид `whisper-cpp`/Vulkan не готов «из коробки»**: в репозитории лежат
  Linux-бинарники (`whisper-native/*.so`, `llama-native/*.so`). Под macOS
  `whisper-cli` и `llama-server` нужно собрать отдельно (Metal/CPU) и указать
  пути в `WHISPER_CPP_BINARY` / `LLM_BINARY`.
- **Самопроверка `doctor`** на macOS учитывает `DYLD_LIBRARY_PATH` при поиске
  разделяемых библиотек.
- **Прослушивание реплик** в вебе и TUI работает через `afplay`.
- **Уведомления о завершении** используют `notify-send` (Linux) — на macOS они
  молча не показываются (мягкий no-op).
- **Шумоподавление (DeepFilterNet)** под Python 3.14 официально не ставится
  (нет колёс под numpy 2.x) — этап просто пропускается.

Итого: базовый CPU-пайплайн (`faster-whisper` + диаризация) на маке
запускается, а GPU-ускорение и нативные движки требуют отдельной сборки.

### Логи

Помимо вывода в консоль, каждый запуск `transcribe` сохраняет полный
DEBUG-лог в файл `<output-dir>/logs/audio-transcriber_ГГГГММДД_ЧЧММСС.log` —
независимо от того, указан ли `--verbose`. Это удобно для диагностики
ошибок (например, отсутствующего токена Hugging Face) постфактум, без
необходимости повторного запуска с `--verbose`.

Обработку можно в любой момент безопасно прервать нажатием `Ctrl+C` —
утилита корректно завершится с сообщением об остановке вместо traceback.

Пример с несколькими форматами экспорта и именами говорящих:

```bash
uv run audio-transcriber transcribe records/call.mp3 \
  --output-dir out/call \
  --model medium \
  --language ru \
  --device auto \
  --format txt --format docx \
  --num-speakers 2 \
  --speaker-name 0=Иван \
  --speaker-name 1=Мария \
  --verbose
```

### Кэш результатов и возобновление после сбоя

Дорогие этапы конвейера — шумоподавление, распознавание речи и диаризация —
кэшируются на диск (по умолчанию `USE_CACHE=true`):

- **Ключ кэша** — хеш от размера и времени изменения исходного аудиофайла плюс
  релевантные параметры стадии (бэкенд и модель ASR, язык, устройство,
  число говорящих, признак денойза и т.п.). Изменился файл или параметр —
  стадия пересчитывается.
- **Где лежит** — `<output-dir>/.cache` (файл на ключ; `CACHE_DIR`/`--cache-dir`
  переопределяют каталог). Это обычные JSON-файлы, их можно удалить руками.
- **Возобновление после сбоя** — если прогон упал на диаризации, готовый
  результат ASR уже сохранён, и при повторе он берётся из кэша, а диаризация
  пересчитывается только она одна.
- **Мягкая деградация** — битый или несовместимый кэш игнорируется с
  предупреждением в лог, стадия пересчитывается; конвейер не падает.
- **Очистка** — флаг `--clear-cache` (или `CLEAR_CACHE=true` в `config.env`)
  удаляет кэш перед запуском; полное отключение — `--no-cache`/`USE_CACHE=false`.

```bash
uv run audio-transcriber transcribe recording.mp3 --clear-cache   # очистить и пересчитать
uv run audio-transcriber transcribe recording.mp3 --no-cache       # не использовать кэш
```

В TUI кэш включается переключателем «Кэш результатов».

### Самопроверка окружения (`doctor`)

Команда `doctor` быстро проверяет окружение (без загрузки моделей и тяжёлых
вычислений) и печатает отчёт со статусами ✓/✗ и подсказками:

```bash
uv run audio-transcriber doctor
```

Проверяются: версия Python, ключевые зависимости (`av`, `faster-whisper`,
`pyannote.audio`, `torch`, `textual`, `pymorphy3`, `deepfilternet`), бинарники
(`whisper-cli`, `llama-server`) и их библиотеки, модели (ggml/GGUF/локальная
pyannote по путям из `config.env`), наличие GPU-Vulkan (через `vulkaninfo` —
не все сборки `whisper-cli` умеют `--list-devices`), `config.env`, токен
Hugging Face (значение **не** выводится), доступность на запись каталогов
результатов и кэша. Код возврата — `0`, если всё критичное в порядке, иначе `1`
(необязательные компоненты дают лишь ✗ без влияния на код возврата). Для
отсутствующих компонентов отчёт показывает, что именно нужно, куда положить
файлы и ссылку на страницу загрузки.

## Архитектура

Проект разбит на независимые компоненты, взаимодействующие через чёткие
интерфейсы (`typing.Protocol`). Это позволяет заменить движок распознавания,
диаризации, коррекции или LLM без изменения остального кода — достаточно
реализовать соответствующий протокол.

Схема отражает фактический порядок вызовов в `pipeline.py`: конвейер строго
последовательный (диаризация начинается только после завершения
распознавания), а не параллельный.

```mermaid
sequenceDiagram
    actor User as Пользователь
    participant UI as CLI / TUI
    participant Config
    participant Pipeline
    participant Denoise as Denoise<br/>(DeepFilterNet, опц.)
    participant ASR as Transcription<br/>(faster-whisper / whisper.cpp)
    participant Diar as Diarization<br/>(pyannote.audio)
    participant Merge as Merging
    participant Sent as SentenceMerger
    participant Correct as Correction<br/>(pymorphy3)
    participant LLM as LLM<br/>(llama.cpp, опц.)
    participant Export as Export

    User->>UI: transcribe audio.mp3 [опции]
    UI->>Config: собрать и провалидировать AppConfig
    Config-->>UI: AppConfig
    UI->>Pipeline: run_pipeline(config)

    opt включён --denoise
        Pipeline->>Denoise: denoise(audio)
        Note right of Denoise: 48 кГц → модель (чанками) →<br/>ресемплинг 16 кГц во временный WAV
        Denoise-->>Pipeline: очищенный аудиофайл
    end

    Pipeline->>ASR: transcribe(audio)
    Note right of ASR: реализует Protocol SpeechRecognizer
    ASR-->>Pipeline: сегменты речи, язык, длительность

    Pipeline->>Diar: diarize(audio)
    Note right of Diar: реализует Protocol SpeakerDiarizer
    Diar-->>Pipeline: сегменты говорящих

    Pipeline->>Merge: merge(сегменты речи, говорящие)
    Merge-->>Pipeline: реплики + говорящие

    Pipeline->>Sent: merge(реплики)
    Note right of Sent: склейка коротких реплик одного<br/>говорящего в предложения
    Sent-->>Pipeline: укрупнённые реплики

    opt включён --enable-correction
        Pipeline->>Correct: correct(реплики)
        Note right of Correct: только неизвестные словоформы (pymorphy3)
        Correct-->>Pipeline: реплики с точечными правками
    end

    opt включён --llm
        Pipeline->>LLM: имена участников + правка терминов
        Note right of LLM: llama-server (Vulkan/CPU),<br/>глоссарий поверх матчера
        LLM-->>Pipeline: реплики + имена
    end

    loop по каждому формату экспорта
        Pipeline->>Export: export(результат, путь)
    end

    Pipeline-->>UI: TranscriptionResult
    UI-->>User: сводка в консоль + файлы в output-dir
```

- **CLI / TUI / Config** — принимают команду или данные формы, валидируют
  параметры запуска (`AppConfig`).
- **Denoise (опционально)** — подавляет фоновый шум (DeepFilterNet) и отдаёт
  один очищенный аудиофайл и распознаванию, и диаризации, чтобы их временные
  метки совпадали. Если движок недоступен — этап пропускается.
- **Transcription / Diarization** — вызываются последовательно, каждый за
  интерфейсом `typing.Protocol`: движок можно заменить (faster-whisper ⇄
  whisper.cpp, другая диаризация) без изменения остального кода. Merging
  сопоставляет их результаты по времени.
- **SentenceMerger** — склеивает подряд идущие короткие сегменты одного
  говорящего в реплики-предложения, чтобы корректор и LLM видели цельный текст.
- **Correction** — опциональное автоисправление опечаток; меняет только слова,
  неизвестные морфологическому анализатору русского языка.
- **LLM** — опциональная постобработка локальным `llama.cpp`: имена участников
  и правка терминов по глоссарию.
- **Export** — сохраняет результат в каждый из запрошенных форматов.

`domain` (модели данных), `progress` (события прогресса для TUI) и `utils`
(логирование, работа с устройством CPU/CUDA, исключения) используются всеми
участниками насквозь и не показаны на схеме отдельно.

### Назначение компонентов

- **`cli`** — точка входа для пользователя. Парсит аргументы командной строки
  через Typer, передаёт их в `config`, обрабатывает ошибки домена
  (`AudioTranscriberError`) и печатает понятные сообщения с корректными кодами
  выхода. Команды: `transcribe`, `tui`, `web`, `glossary` и `doctor`.
- **`tui`** — интерактивный интерфейс на Textual: очередь, живой прогресс по
  событиям `progress`, поиск по стенограмме. Точка входа и компоновка — в
  `app.py`, детали разнесены по модулям (`screens`, `widgets`, `messages`,
  `queue`, `config_builder`, `options`, `formatting`, `results`, `constants`).
  Работает поверх того же `run_pipeline`; больше не развивается.
- **`web`** — локальный веб-интерфейс: FastAPI-сервер на `127.0.0.1`, REST API
  под `/api` (файлы, очередь задач, SSE-прогресс, результат, образцы голоса,
  правка говорящих, глоссарий, настройки, протокол, доктор) и раздача собранного
  SPA из `web/static`. Дополнительно: каталог и фоновое скачивание моделей
  (`models.py`), секреты — HF-токен в файле с правами `0600` (`secrets.py`),
  длительности стадий (`timings.py`) и план мастера первого запуска (`setup.py`).
  Фоновая очередь — один воркер (`runner.py`); данные и БД задач — в каталоге
  `web-data/`. Запускается командой `audio-transcriber web`.
- **`storage`** — SQLite-хранилища (только стандартный `sqlite3`): БД глоссария
  (`glossary_db.py`) с источниками и терминами, импортом TXT/CSV, и сборка
  глоссария для матчера с авто-миграцией из `GLOSSARY_PATH`
  (`glossary_builder.py`).
- **`protocol`** — формирование «протокола» встречи по запросу (стенограмма +
  резюме + экспорт); вызывается кнопкой в веб-версии и TUI, резюме
  пересчитывается по актуальной стенограмме.
- **`config`** — превращает «сырые» аргументы CLI в валидированный `AppConfig`
  (dataclass): проверяет существование входного файла, создаёт выходную
  директорию, разбирает пользовательские имена говорящих и пути глоссариев.
- **`domain`** — модели данных (`dataclass`), которыми обмениваются все
  остальные слои: сегменты речи, сегменты говорящих, финальные реплики
  стенограммы. Не содержит логики и не зависит ни от одной из библиотек
  распознавания/диаризации/экспорта. `editing.py` — чистые функции правки
  говорящих (переименование, объединение) по готовому результату.
- **`transcription`** — распознаёт речь через `WhisperSpeechRecognizer`
  (faster-whisper) или `WhisperCppRecognizer` (whisper.cpp/Vulkan); оба
  реализуют протокол `SpeechRecognizer`.
- **`diarization`** — определяет говорящих через `PyannoteSpeakerDiarizer`
  (pyannote.audio, в т.ч. локальная модель), реализующий протокол
  `SpeakerDiarizer`; `energy.py` — энергетические помощники для выбора участков
  речи, `samples.py` — авто-извлечение образцов голоса, `voices.py` —
  библиотека образцов из каталога `VOICES_DIR`.
- **`denoising`** — шумоподавление через `DeepFilterDenoiser` (DeepFilterNet),
  реализующий протокол `DenoiserProtocol`. Работает на 48 кГц потоково чанками
  с overlap-add, отдаёт готовый WAV 16 кГц моно (декодирование/ресемплинг —
  через `utils.audio`). Мягко деградирует: при отсутствии движка или сбое
  возвращает исходный путь.
- **`cache`** — постадийный кэш дорогих этапов: `StageCache` (ключ по
  файлу+параметрам, JSON/WAV на диске, мягкая деградация и очистка),
  сериализация сегментов ASR/диаризации и `CachingDenoiser` — обёртка над
  `DenoiserProtocol`. Встраивается в `pipeline.py`.
- **`cleaning`** — очистка и нормализация текста: `ArtifactCleaner` (пометки,
  «голые» шумовые слова, шаблонные галлюцинации, реплики «почти без текста на
  длинном интервале»), `RepetitionCleaner` (схлопывание повторов) и
  `TextNormalizer` (безопасная пунктуация/пробелы); каждый — за своим протоколом.
- **`merging`** — сопоставляет по времени сегменты речи (`transcription`) и
  сегменты говорящих (`diarization`), формируя реплики `TranscriptEntry`; затем
  `SentenceMerger` склеивает подряд идущие короткие реплики одного говорящего.
  `overlap.py` помечает зоны наложения речи и добирает сов-говорящих реплики.
- **`correction`** — автоисправление опечаток через `MorphTextCorrector`.
  Для неизвестных словоформ подбирается ближайшая известная форма русского
  языка (`pymorphy3` / OpenCorpora); известные слова и склонения не изменяются.
- **`llm`** — локальная LLM-постобработка: клиент к `llama-server`
  (`client.py`, Vulkan/CPU, гарантированная очистка процессов), глоссарий с
  детерминированным матчером (`glossary.py`) и связка обоих в извлечение имён
  и правку терминов (`postprocess.py`).
- **`progress`** — `ProgressEvent`/`ProgressCallback`: единый канал событий о
  ходе обработки, который используют CLI, TUI и компоненты конвейера.
- **`doctor`** — быстрая самопроверка окружения (Python, зависимости,
  бинарники и модели, GPU-Vulkan через `vulkaninfo`, `config.env`, токен,
  доступность каталогов); печатает отчёт ✓/✗ и задаёт код возврата команды
  `doctor`.
- **`export`** — сохраняет готовый `TranscriptionResult` в выбранные форматы.
  Контракт `ResultExporter` позволяет добавлять новые форматы без изменения
  остального кода.
- **`utils`** — общие для всех слоёв утилиты: иерархия исключений
  (`exceptions.py`), настройка логирования через `rich` (`logging.py`),
  определение/резолвинг вычислительного устройства CPU/CUDA (`device.py`),
  декодирование аудио через PyAV (`audio.py`), локальное проигрывание образцов
  без блокировки интерфейса (`playback.py`) и ограничение длины `--hotwords`
  (`hotwords.py`).
- **`pipeline.py`** — точка сборки конвейера: (денойз) → распознавание →
  диаризация → объединение → очистка → склейка реплик → (коррекция) → (LLM) →
  экспорт. Дорогие стадии обёрнуты в постадийный кэш (`cache`) при `use_cache`.
  При `protocol_auto=false` (веб/TUI) резюме и экспорт на прогоне не выполняются
  — их формирует протокол по кнопке. Используется CLI, TUI и веб-версией (через
  `web.runner`).

## Тестирование

Тесты написаны на `pytest` (850+ тестов) и лежат в `tests/`, зеркалируя
структуру `src/`. Линтер Ruff и проверка типов mypy проходят без замечаний.

Запуск всех быстрых тестов (без интеграционных):

```bash
uv run pytest
```

Подробный вывод по каждому тесту:

```bash
uv run pytest -v
```

Запуск тестов только для конкретного модуля, например конфигурации:

```bash
uv run pytest tests/test_config_settings.py
```

С отчётом о покрытии кода (требует `pytest-cov`, при необходимости
установите через `uv add --dev pytest-cov`):

```bash
uv run pytest --cov=audio_transcriber
```

`pytest` уже настроен в `pyproject.toml` (`[tool.pytest.ini_options]`), так
что дополнительная конфигурация не требуется — команда `uv run pytest`
работает сразу после `uv sync`.

### Интеграционные тесты

`tests/test_integration.py` прогоняет полный конвейер (распознавание →
объединение → склейка реплик → экспорт во все форматы) на реальной короткой
записи `tests/tests_jfk.flac`. Такие тесты помечены маркером `integration` и
**не** запускаются по умолчанию (см. `addopts` в `pyproject.toml`), так как при
первом запуске скачивают модель распознавания:

```bash
uv run pytest -m integration
```

Диаризация в этом тесте подменена заглушкой с одним говорящим — готовые модели
pyannote.audio требуют отдельного токена доступа Hugging Face (см. раздел
[«Токен доступа для диаризации»](#токен-доступа-для-диаризации)), что не нужно
для проверки связки распознавание → объединение → склейка → экспорт.

### Линтер и проверка типов

В проекте настроены [Ruff](https://docs.astral.sh/ruff/) (линт + сортировка
импортов) и [mypy](https://mypy-lang.org/) — конфигурация в `pyproject.toml`
(`[tool.ruff]`, `[tool.mypy]`). Оба инструмента входят в dev-группу и
устанавливаются через `uv sync`.

```bash
uv run ruff check src tests        # линт
uv run ruff format --check src     # проверка форматирования
uv run mypy                        # проверка типов (src/)
```

## Разработка

Зависимости для разработки (`pytest`, `ruff`, `mypy`) объявлены в отдельной
dev-группе `pyproject.toml` и устанавливаются автоматически при `uv sync`.

Добавить новую зависимость:

```bash
uv add <package>          # обычная зависимость
uv add --dev <package>    # зависимость для разработки/тестов
```

## Версионирование и история изменений

Проект следует [Semantic Versioning](https://semver.org/lang/ru/): версия
хранится в единственном месте — в `pyproject.toml` (поле `version`), а
`__version__` читается из метаданных пакета. Каждый релиз отмечается git-тегом
`v<версия>` (первый — `v0.1.0`). Значимые изменения перечислены в
[CHANGELOG.md](CHANGELOG.md).
